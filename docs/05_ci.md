# 05. CI (継続的インテグレーション) を見る

所要の目安: **約10分** (**デモ・閲覧のみ**。参加者が CI を新規作成する必要はありません) 

オーナーの本番的な Julia パッケージ設定は [DistSSHRun.jl](https://github.com/yamanori99/DistSSHRun.jl) を参考にしています。本教材リポジトリ ([JuliaGitHubCursorIntro.jl](https://github.com/daihiko-lab/JuliaGitHubCursorIntro.jl)) では、**参加者が読みやすいようにかなり簡略化** しています (詳細は下記「参考にした点 / 省いた点」) 。当日参加者の PR は **Private ハンズオン用コピー** 上で動く CI を見ますが、設定の考え方は同じです。

## 1. CI とは

**CI (Continuous Integration)** は、コードを GitHub に送るたびに、決まったチェック (テストやフォーマット確認など) を **自動で実行** する仕組みです。

このリポジトリでは **GitHub Actions** を使います。設定ファイルは `.github/` 以下にあります。

---

## 2. いつ動くか

ワークフロー名 **Test** ([`.github/workflows/CI.yml`](../.github/workflows/CI.yml)) は次のときに走ります。

| トリガー | 意味 |
|----------|------|
| **`pull_request`** | PR の作成・更新 (参加者の PR 課題でここが主役) |
| **`push` (`main` のみ)** | `main` にマージされたあと |
| **`workflow_dispatch`** | オーナーが手動実行 (デモ用) |
| **`schedule` (cron)** | **月1回** (`main` 上)。コードを変えていなくても、レジストリ側の依存更新などで壊れていないかを確認する |

**定期実行の目的**: 教材リポジトリはしばらく触らなくても、Julia パッケージの新版が出ると将来 `instantiate` や CI が失敗することがあります。月次の **JETLS (1.13) と Ubuntu テスト** を回すと、早期に気づけます (参加者向け PR とは別の「健康診断」です) 。

PR を出すと、数分以内に **Checks** にジョブ名が並び始めるのが普通です。

`CI.yml` の **concurrency** は、PR 上では **進行中の古いランをキャンセル** します (`cancel-in-progress`)。同じブランチへ連続 push しても、完了しなかったランが残り続けるのを防ぎ、Actions の消費を抑えます。

### PR でチェックが 0 件に見えるとき

- **走っている最中** (まだ GitHub が表示を更新していない) 
- **連続 push** で古いランが **キャンセル** された直後 (本リポジトリは PR 時だけ古いランを止める設定です) 
- **`main` にまだワークフローが無い** 状態の最初の PR … マージ後の次回からは安定しやすい

Actions タブ (リポジトリ → **Actions**) で Run の状態を見ると確実です。

## 3. PR 画面での見方

1. GitHub で自分の PR を開く
2. ページ下部付近の **Checks** (またはコミット横の **✓ / ✗**) を見る
3. すべて **緑 (pass)** なら合格ライン  
4. **赤 (fail)** のときは、失敗したジョブ名をクリックして **ログ (Log)** を開く

### ログの読み方のコツ

- **下にスクロール** すると、エラーメッセージの塊が出ることが多い
- `ERROR:` や `Test Failed` などを探す
- ローカルで再現:

  ```bash
  julia --project=. -e 'using Pkg; Pkg.instantiate(); Pkg.test()'
  ```

## 4. このリポジトリで走るチェック (PR で見えるもの) 

**ワークフロー Test** (`CI.yml`) では、**Runic → JETLS (1.13) → テスト** の順でゲートをかけています。別ワークフローで **actionlint** と **Gitleaks** も走ります。

| チェック名 (例) | 目的 (一言) |
|------------------|-------------|
| **Runic** | Julia ソースの **フォーマット** が揃っているか (`fredrikekre/runic-action`) |
| **JETLS (1.13, ubuntu-latest, x64)** | Julia の **静的解析** (`jetls check`)。失敗すると Test ワークフロー内のテストはスキップ |
| **JuliaGitHubCursorIntro (1, ubuntu-latest)** | **`Pkg.test()`** でパッケージ動作と **Aqua** による品質チェック (Ubuntu のみ) |
| **actionlint** ([`actions-lint.yml`](../.github/workflows/actions-lint.yml)) | **GitHub Actions の YAML** に文法・よくある誤りがないか |
| **Gitleaks** ([`gitleaks.yml`](../.github/workflows/gitleaks.yml)) | コミット履歴に **API キーなどの秘密情報** が混ざっていないか |

DistSSHRun.jl は actionlint に加え zizmor / pinact なども回しますが、本教材は **actionlint のみ** に簡略化しています。

README のバッジは **Test / cov (Codecov) / Julia 1.13+ / MIT / Runic** の 5 つだけです。**JETLS・Aqua・actionlint・Gitleaks** はバッジにせず、下記のとおり CI で実行します。

- **Runic** … フォーマット
- **テスト** (`JuliaGitHubCursorIntro (1, ubuntu-latest)`) … `Pkg.test()` (提出物の実行確認を含む) 
- **JETLS (1.13)** … `src/`・`examples/`・`submissions/` の静的解析 (`test/runtests.jl` は Test 依存のため対象外)
- **Aqua** … `test/runtests.jl` 内の `Aqua.test_all` (独立ジョブではない) 
- **actionlint** … ワークフロー YAML 検査
- **Gitleaks** … 秘密情報スキャン
- **月次 `schedule`** … `main` 上で依存の健康診断 (PR では走らない日時もある) 

**ruleset 用のチェック名 (GitHub PR 画面の表示例)**:

| ワークフロー | ジョブ名 (そのまま指定) |
|--------------|-------------------------|
| **CI** | `Runic` |
| **CI** | `JETLS (1.13, ubuntu-latest, x64)` |
| **CI** | `JuliaGitHubCursorIntro (1, ubuntu-latest)` |
| **Actions lint** | `actionlint` |
| **Scan** | `Gitleaks` |

### Gitleaks と Organization ライセンス

DistSSHRun.jl は **`gitleaks/gitleaks-action`** を使います。**Organization リポジトリ** では同アクションが **`GITLEAKS_LICENSE`** (有料ライセンス) を要求することがあります ([公式の案内](https://github.com/gitleaks/gitleaks-action#-announcement)) 。

本教材では **OSS の gitleaks コマンド** を CI から直接実行し、ライセンスキーなしで秘密情報パターンを検査します。オーナーが Organization 方針で **gitleaks-action + `GITLEAKS_LICENSE`** に切り替える場合は、GitHub **Secrets** への登録が **オーナー作業** です (エージェントでは外部契約・Secret 登録は行いません) 。

### キャッシュ (`julia-actions/cache`)

DistSSHRun.jl と同様、**`cache-scratchspaces: false`** と **`delete-old-caches: false`** を使います。

- **テストジョブ**: 標準の Julia パッケージキャッシュ
- **JETLS ジョブ**: `cache-name` に Julia バージョンと `JULIA_CPU_TARGET` のハッシュを入れ、ジョブごとに分離
- **JETLS アプリ本体**: composite action 内で `~/.julia/bin/jetls` などを `actions/cache` で保持 (DistSSHRun と同じ考え方)

スクラッチスペースをキャッシュに含めないのは、壊れた `registry_updates.toml` が復元される事故を避けるためです (DistSSHRun のコメント参照) 。

### Codecov (カバレッジ)

`main` への push 時だけ、`julia-runtest` → `julia-processcoverage` → [Codecov](https://codecov.io/gh/daihiko-lab/JuliaGitHubCursorIntro.jl) へアップロードします (DistSSHRun.jl と同様に **OIDC** 、`fail_ci_if_error: false` で Codecov 未連携時も PR 開発を止めない) 。README のカバレッジバッジは **Codecov 側で `daihiko-lab/JuliaGitHubCursorIntro.jl` を有効化したあと** `main` でテストが走ると表示されます。

## 6. DistSSHRun.jl を参考にした点 / 意図的に省いた点

### 参考にした点

- ワークフロー名 **Test**、`on: pull_request` + `push: main` + `workflow_dispatch` + **月次 `schedule`**
- **`permissions: contents: read`** の明示
- **PR のみ** `cancel-in-progress` (連続 push で同じブランチの古いランを止め、重複実行を減らす) 
- **Runic / JETLS (1.13 のみ)** を独立ジョブにし、テストの前段にする
- **`fredrikekre/runic-action`**、**`.github/actions/jetls-check`** (JETLS rev ピン付き)
- **`julia-actions/cache`** で `cache-scratchspaces: false` (JETLS 用の `cache-name` 付き)
- **`main` push 時の Codecov** (`julia-processcoverage` + `codecov-action`、OIDC)
- DistSSHRun 本家は **アクションの SHA 固定** + **setup-julia/cache v3** (本教材は Dependabot 向けに `@v4` / `@v2` タグで簡略化) 
- **Dependabot**: `github-actions` + `julia` (CompatHelper ワークフローは使わない) 

### 省いた点 (導入会用に簡略化) 

- マルチパッケージ・`detect` ジョブ・パスフィルタ
- 独立した **Aqua ジョブ** (本教材は `Pkg.test()` 内の Aqua に集約) 、PkgEval / SSH E2E / WSL2 など (JETLS は **1.13 のみ・簡略版** 。macOS / Windows テスト、Julia 1.14-pre の JETLS も省略。Codecov は **main のみ** ・単一 OS)
- 月次の別 `runic.yml`、カスタム composite actions
- **TagBot** (自動タグ・Release。教材リポジトリではワークフローを置かない方針) 
- Documenter・zizmor / pinact (actionlint は **別ワークフローで採用**) ・大量のラベル用ワークフロー

本格的な例は [DistSSHRun.jl の `.github`](https://github.com/yamanori99/DistSSHRun.jl/tree/main/.github) を見てください。

## 7. 落ちたときに参加者が確認すること

1. ローカルで `] instantiate` 後、`Pkg.test()` が通るか
2. `submissions/ユーザー名.jl` にタイポや構文エラーがないか
3. ローカルで `julia -m Runic -c .` が通るか (Ubuntu ジョブと同等) 
4. 直したら **もう一度 commit → push** → 同じ PR 上で CI が再実行される
