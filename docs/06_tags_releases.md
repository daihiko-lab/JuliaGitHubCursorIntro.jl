# 06. タグ (tag) と GitHub リリース

所要の目安: **約5分** (**説明とデモ用**。参加者全員がタグを打つハンズオンにはしません) 

PR で「今の変更を取り込んでください」と提案するのに対し、**タグ**と**リリース**は「**この時点のコードに名前を付けて残す**」ための仕組みです。研究では、論文投稿時点の分析コードを後から同じ状態で参照できるようにする場面でよく使います。

---

## 1. タグとは

**タグ (tag)** は、Git の履歴のうち **特定のコミット** に付ける **固定のラベル (名前)** です。

- **ブランチ** … 先端が動き、新しいコミットが積み上がっていく「枝」
- **タグ** … あるコミットに針を刺したような「しおり」 (基本的に動かさない) 

タグはローカルでも GitHub 上でも一覧でき、**そのコミットのスナップショットを素早く指定** できます。

代表的な用途:

- ソフトウェアの **v1.0.0** のような版の記録
- 論文 **投稿日・査読提出日** に対応するコードの固定
- Zenodo などと連携して **永続的なアーカイブ** を作るときの基点

## 2. `git tag` と `git push --tags` の基本

### 軽いタグ (名前だけ付ける) 

```bash
# 現在チェックアウトしているコミットにタグを付ける
git tag v0.1.0-demo

# 特定のコミットに付ける (COMMIT は git log で調べたハッシュ) 
git tag v0.1.0-demo COMMIT
```

### 注釈付きタグ (メッセージ付き・リリース向き) 

```bash
git tag -a v0.1.0 -m "初回デモ用リリース"
```

### 確認

```bash
git tag              # タグ一覧
git show v0.1.0      # タグが指すコミットの内容
```

### GitHub へ送る

タグは **通常の `git push` では送られません**。明示的に push します。

```bash
# 1 個だけ送る
git push origin v0.1.0

# ローカルのタグをまとめて送る
git push --tags
```

> **注意**: `git push --tags` は **ローカルにあるすべてのタグ** をリモートに送ります。練習用タグを消し忘れないよう、デモではオーナーが操作する想定です。

### タグを外す (参考) 

```bash
git tag -d v0.1.0-demo              # ローカル
git push --delete origin v0.1.0-demo  # GitHub 上
```

## 3. GitHub の Releases でリリースを作る

GitHub の **Releases** は、タグと組み合わせて「この版の説明・添付ファイル・公開ページ」を整える機能です。

### 手順 (ブラウザ) 

1. リポジトリを開く → 右サイドバーまたは **Releases** (`/releases`) 
2. **Draft a new release** (新規リリースを作成) 
3. **Choose a tag** … 既存タグを選ぶか、**新しいタグ名** (例: `v0.1.0`) を入力して作成
4. **Target** … タグを付けたい **ブランチまたはコミット** (通常は `main` の安定版) 
5. **Release title** … 人が読むタイトル (タグ名と同じでも可) 
6. **Describe this release** … 変更点のメモ (マークダウン可) 
7. 必要なら **Attach binaries** でファイルを添付 (教材では省略可) 
8. **Publish release** で公開 (下書きなら **Save draft**) 

公開後、リポジトリのトップからその版のコードを **ZIP / ソース** としてダウンロードできます。

### Cursor / ターミナルとの関係

- タグは **Git コマンド** でも、**Releases 作成時に GitHub 上で** でも作れます
- 研究用は **注釈付きタグ + Releases の説明文** を残すと、後から「何の版か」が分かりやすいです

## 4. バージョン番号 (セマンティックバージョニングの概要) 

多くのプロジェクトでは **SemVer (Semantic Versioning)** と呼ばれる `メジャー.マイナー.パッチ` 形式を使います。

形式: **`v1.2.3`** (先頭の `v` は慣習) 

| 部分 | 上げるタイミングの目安 |
|------|------------------------|
| **メジャー** (1.x.x) | 互換性のない大きな変更 |
| **マイナー** (x.2.x) | 後方互換のある機能追加 |
| **パッチ** (x.x.3) | 後方互換のバグ修正 |

分析スクリプトや再現用リポジトリでも、`v1.0.0` (論文用の初版) 、`v1.0.1` ( typo 修正のみ) のように付けることがあります。**ゼミの入門では厳密に守る必要はありません**が、「版の名前」として使うと整理しやすいです。

Julia の `Project.toml` にある **`version` 欄** も、プロジェクトの **論理的な版** を示します (Git のタグ名と揃えると分かりやすい) 。

## 5. 研究で使う場面

### 論文投稿時点のコードを固定する

査読中や論文掲載後に、「当時の分析を再実行したい」「査読者が同じ結果を再現したい」という要件が出ます。そのとき **投稿直前のコミットにタグ** (例: `v1.0.0-submitted-2026-03-15`) を付けておくと、

- 後から `git checkout v1.0.0-submitted-2026-03-15` で同じツリーに戻れる
- GitHub Releases からその時点の ZIP を取得できる

といった運用がしやすくなります。

### Zenodo と DOI (軽い紹介) 

[Zenodo](https://zenodo.org/) は、研究データやソフトウェアを **長期アーカイブ** し、**DOI (Digital Object Identifier)** を付与できるサービスです。GitHub リポジトリやリリースと連携し、**引用しやすい永続リンク** を得る研究者が多いです (GitHub → Zenodo の連携設定は本ゼミの範囲外ですが、「タグ・リリースで区切った版をアーカイブできる」イメージを持っておくとよいです) 。公開時の **ライセンス** の考え方は [08_licensing.md](08_licensing.md) も参照してください。

Julia パッケージを General に登録したあとの **TagBot** (タグ・Release 自動化) は [07_github_for_julia.md](07_github_for_julia.md) を参照してください。**本ゼミ用リポジトリでは TagBot は導入していません** (自動タグ・Release の扱いに注意が必要なため) 。
